## 1. Purpose

Editors and readers on a news platform need a fast way to understand the substance of an article — its key facts, entities, and claims — without reading it in full. This document defines the business requirements for a small application that accepts submitted article text and returns a structured, AI-generated briefing of that article.

This is a scoped take-home exercise, not a production system. Requirements are deliberately minimal and favor a focused, well-reasoned implementation over feature completeness.

## 2. Background

Articles can be long and dense, containing many people, organizations, events, and claims. Editors and readers currently must read an article in full to extract this information manually, which is slow and doesn't scale. An AI-powered briefing tool can compress this effort into a single structured view generated on demand.

## 3. Objectives

- Let a user submit raw article text and receive a useful, structured briefing generated by an LLM.
- Demonstrate sound product judgment in deciding what a "useful briefing" contains, since the brief leaves this open-ended.
- Demonstrate an application design that treats the LLM as an unreliable external dependency and degrades gracefully when it fails or returns malformed output.
- Deliver a simple, usable interface for entering text, submitting it, and reading the result.

## 4. Scope

### 4.1 In scope
- A UI for pasting/entering article text and submitting it for analysis.
- A backend/service layer that calls an LLM to analyze the submitted text and returns a structured briefing.
- Definition of the briefing's content (see Section 6).
- Handling of loading, empty, error, timeout, and malformed-output states.
- A README covering setup, technology choices, analysis approach, architectural/product decisions, trade-offs, assumptions, and AI-tool usage.
- Automated tests for the areas of highest value (see Section 9).

### 4.2 Out of scope
- User accounts, authentication, or authorization.
- Persistent storage of articles or briefings across sessions (beyond what's needed to display a single result), unless a lightweight history proves trivial to add.
- Multi-article batch processing.
- Editorial workflow features (publishing, approvals, commenting, versioning of briefings).
- Production-grade infrastructure: scaling, observability stacks, CI/CD pipelines, deployment to hosting.
- Support for non-text article inputs (URLs to scrape, PDFs, images).
- Fact-checking / verification of claims against external sources — the briefing may flag claims as checkable, but does not verify them.

## 5. Stakeholders / Users

| Role | Interest |
|---|---|
| Editor | Wants to quickly triage an article: who/what it's about, what's newsworthy, how to classify it. |
| Reader | Wants a fast, digestible overview before deciding whether to read the full article. |
| Reviewer (hiring team) | Wants to assess product judgment, engineering quality, and use of AI tooling. |

## 6. Functional Requirements

### FR1 — Article submission
The user must be able to enter or paste the full text of an article into the UI and submit it for analysis. Empty or trivially short submissions must be rejected client-side with a clear message before any request is sent.

### FR2 — Article briefing generation
On submission, the backend sends the article text to an LLM and requests a structured analysis. The briefing returned to the user should include, at minimum:

- **Summary** — a concise (2–4 sentence) plain-language summary of the article.
- **Key points** — a short list of the most important facts or developments.
- **Entities** — people, organizations, and locations mentioned, grouped by type.
- **Topics/category** — one or more topic tags and a suggested editorial category (e.g. Politics, Business, Technology, Sports).
- **Checkable claims** — a short list of specific, factual, potentially verifiable statements extracted from the article (explicitly not fact-checked by the system).

This list defines the minimum useful briefing; the implementer may extend it if it adds clear value without bloating the response.

### FR3 — Result presentation
The UI must present the briefing in a clearly organized, scannable layout (not a raw JSON/text dump), and must visually distinguish the different sections in Section 6/FR2.

### FR4 — Loading state
While analysis is in progress, the UI must indicate that a request is running and prevent duplicate submissions.

### FR5 — Error handling
If the LLM call fails, times out, or returns output that cannot be parsed into the expected structure, the UI must show a clear, user-facing error rather than a blank state, broken layout, or raw stack trace. The user must be able to retry.

### FR6 — Partial / insufficient content handling
If the article text is too short, too ambiguous, or lacks enough information for a given section of the briefing (e.g. no named entities present), that section must degrade gracefully (e.g. "No entities found") rather than causing the entire request to fail or displaying fabricated content.

### FR7 — Input guardrails
The system should apply reasonable limits on input size and should treat submitted text as untrusted data passed to a third-party LLM (i.e., no execution of instructions embedded in the article text beyond the defined analysis task).

## 7. Non-Functional Requirements

- **Usability** — a first-time user should be able to complete a submission and read a result without instructions.
- **Resilience** — the application must not crash or hang indefinitely on LLM failure; a sensible timeout must be enforced.
- **Maintainability** — code should be organized so the LLM integration, API layer, and UI are separable and individually testable.
- **Transparency** — the README must disclose AI-tool usage per the brief's requirements, including one example of AI-generated output that was changed, rejected, or significantly improved.
- **Security** — no API keys, credentials, or secrets committed to the repository; secrets supplied via environment configuration only.

## 8. Assumptions & Constraints

- The company will provide access to an LLM for use during the exercise; the exact provider/model is a technical decision to be made during implementation and documented in the README, not fixed by this BRD.
- Article text is provided as plain text pasted by the user, in English, of typical news-article length (up to a few thousand words).
- No requirement for real-time collaboration or multi-user concurrency.
- The exercise is time-boxed to ~3–4 hours; scope must be prioritized accordingly, with any deferred work explicitly documented rather than left unexplained.

## 9. Testing Expectations

Automated tests should focus on the areas of highest risk/value rather than full coverage:

- Parsing/validation of LLM output (including malformed or incomplete responses).
- Error and timeout handling paths.
- Core UI states: empty, loading, success, error.

## 10. Deliverables (per brief)

1. A GitHub repository containing the solution.
2. A README covering: how to run the app, technologies/libraries chosen, approach to article analysis, architectural/product decisions, trade-offs and assumptions, and AI-tool usage.
3. Tests where they provide the most value.

## 11. Success Criteria

- A user can paste article text, submit it, and receive a structured briefing covering the fields in FR2 within a reasonable time.
- The application behaves predictably and communicates clearly when the LLM is slow, fails, or returns unusable output.
- The README allows a reviewer to run the project locally without additional context and understand the reasoning behind key decisions.

## 12. Open Questions (to resolve during implementation)

- Which LLM provider/model and SDK to use, and how prompts will be structured to elicit reliably-structured output (e.g. JSON schema / function-calling vs. free text + parsing).
- Whether any briefing history/persistence is worth the (small) added complexity within the time box.
- Exact set of entity types and category taxonomy to support out of the box.
